# سامانه مدیریت نهار، ژتون غذا، مهمان و پذیرایی سازمانی (وینک)

پلتفرم وب داخلی مبتنی بر **Django 5** برای مدیریت نهار و ژتون غذا، مهمان‌ها و
کارت‌های موقت، و درخواست‌های پذیرایی ویژه. سیستم بدون دستگاه تردد به‌صورت کامل کار
می‌کند و ساختار آن برای اتصال آیندهٔ دستگاه تردد، کارت و اثر انگشت آماده شده است.

## معماری و اپ‌ها

| اپ | مسئولیت |
|---|---|
| `core` | مدل پایه (TimeStamped)، توابع تاریخ شمسی، میکسین دسترسی، فرم Bootstrap |
| `accounts` | کاربر سفارشی با نقش سازمانی، ورود/خروج |
| `people` | مدیریت پرسنل و عوامل سازمان |
| `guests` | مهمان، کارت موقت مهمان، تخصیص کارت |
| `meals` | ژتون غذا، برنامه نهار روزانه، لاگ مغایرت + **لایه سرویس قواعد** |
| `catering` | درخواست پذیرایی، اقلام، جزئیات اقلام |
| `attendance` | لایه آمادهٔ اتصال دستگاه تردد (مدل رویداد، بدون اتصال واقعی) |
| `reports` | گزارش‌ها با فیلتر تاریخ و خروجی Excel |
| `dashboard` | داشبورد آماری روزانه |

**اصل کلیدی:** تمام تصمیم‌گیری (صدور ژتون، جلوگیری از تکرار، مصرف) در
`meals/services.py` متمرکز است تا هم وب و هم پردازش آیندهٔ دستگاه تردد از یک منطق
واحد استفاده کنند. منبع تصمیم سایت است، نه دستگاه.

## مدل‌ها و قواعد مهم

- **یک ژتون معتبر در روز برای هر فرد:** با `UniqueConstraint` مشروط (به‌جز ژتون
  لغوشده) روی `(date, personnel)` و `(date, guest)` در سطح دیتابیس تضمین می‌شود.
- **ثبت مغایرت:** هر تلاش تکراری برای صدور یا مصرف نامعتبر در `DuplicateAttempt`
  لاگ می‌شود (خارج از تراکنشِ خطا تا پاک نشود) و در داشبورد/گزارش‌ها دیده می‌شود.
- **ژتون فقط همان‌روز و یک‌بار مصرف:** مصرف مجدد، ژتون لغوشده و ژتون روز دیگر رد
  می‌شوند.

## نقش‌ها و دسترسی

`admin` (مدیر سیستم)، `reception` (پذیرش/نگهبانی)، `restaurant` (مسئول رستوران)،
`protocol` (واحد تشریفات)، `host` (مدیر واحد / میزبان)، `office_manager`
(مدیر اداری)، `supply` (واحد تأمین)، `report_viewer` (گزارش‌گیر). کنترل دسترسی با
`core.mixins.RoleRequiredMixin` و منوی نقش‌محور انجام می‌شود.

### محل پذیرایی و جلوگیری از تداخل

محل‌های پذیرایی به‌صورت لیست تعریف می‌شوند (واحد تشریفات). هر درخواست پذیرایی یک
محل و بازهٔ زمانی (ساعت شروع/پایان) دارد؛ اگر همان محل در بازهٔ متداخل قبلاً رزرو شده
باشد، سیستم اجازهٔ ثبت نمی‌دهد.

### اطلاع‌رسانی ایمیلی

فقط برای **میزبان‌ها** و **مدیر اداری** ایمیل ارسال می‌شود:

- ثبت درخواست جدید (مهمان یا پذیرایی) که در انتظار تأیید است → ایمیل به مدیر اداری.
- پس از تأیید/رد توسط مدیر اداری → ایمیل به میزبانِ ثبت‌کننده.

تنظیمات در `.env` (کلیدهای `EMAIL_*`، `DEFAULT_FROM_EMAIL`، `NOTIFY_EMAIL_ENABLED`).
در توسعه پیش‌فرض `console` است (ایمیل در ترمینال چاپ می‌شود)؛ برای ارسال واقعی،
`EMAIL_BACKEND` را به SMTP سازمان تغییر دهید. ایمیل کاربران از فیلد ایمیل آن‌ها
خوانده می‌شود (در پنل مدیریت یا با دستورهای seed قابل تنظیم).

### واحد تأمین (خرید اقلام)

هر قلمِ درخواست پذیرایی می‌تواند «نیاز به خرید» علامت بخورد. این اقلام در پنل
**واحد تأمین** (`/catering/supply/`) فهرست می‌شوند تا تهیه و «تهیه‌شده» ثبت گردند.

### گردش‌کار تأیید مهمان

مدیر واحد (`host`) مهمان را ثبت می‌کند؛ مهمان در وضعیت «در انتظار تأیید» قرار
می‌گیرد و مدیر اداری (`office_manager`) آن را در صفحهٔ «تأیید مهمان‌ها» تأیید یا رد
می‌کند. فقط مهمان‌های تأییدشده قابل تخصیص کارت هستند.

## راه‌اندازی

```bash
python -m venv .venv
source .venv/bin/activate           # ویندوز: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env                 # و در صورت نیاز ویرایش کنید

python manage.py migrate
python manage.py seed_demo           # کاربران و دادهٔ نمونه (اختیاری)
python manage.py runserver
```

سپس به `http://127.0.0.1:8000/` بروید.

### کاربران نمونه (پس از `seed_demo`)

| نام کاربری | نقش | رمز |
|---|---|---|
| `admin` | مدیر سیستم | `admin12345` |
| `reception` / `restaurant` / `protocol` / `host` / `reporter` | سایر نقش‌ها | `test12345` |

## تغییر دیتابیس نهایی

در فایل `.env` مقدار `DB_ENGINE` را به `postgres` یا `mssql` تغییر داده و مشخصات
اتصال را وارد کنید. سپس درایور مربوطه را از `requirements.txt` نصب کنید.

## سطح دسترسی (Group / Permission)

علاوه بر کنترل دسترسی نقش‌محورِ وب (`RoleRequiredMixin`)، یک دستور، گروه‌های استاندارد
جنگو را با مجوزهای متناسبِ هر نقش می‌سازد و کاربران را به گروه نقش خود می‌افزاید:

```bash
python manage.py setup_roles
```

### کاربران میزبانِ واحدها

برای هر واحد سازمانی یک کاربر میزبان (نقش `host`) ساخته می‌شود که می‌تواند مهمان
ثبت کند و درخواست پذیرایی بزند:

```bash
python manage.py create_unit_hosts
```

واحدها: فنی مهندسی، مالی، اداری، فناوری اطلاعات، منشی دفتر مدیریت، تامین،
برنامه‌ریزی و لجستیک. نام کاربری‌ها مانند `host_eng`، `host_finance` و … با رمز
اولیهٔ `host12345` (پس از اولین ورود تغییر دهید).

## استقرار در Production

```bash
# ۱) تنظیمات
cp .env.production.example .env        # و مقادیر را تکمیل کنید (SECRET_KEY، دیتابیس، دامنه)

# ۲) دیتابیس و دسترسی‌ها
python manage.py migrate
python manage.py setup_roles

# ۳) جمع‌آوری فایل‌های استاتیک (WhiteNoise، فشرده و نسخه‌دار)
python manage.py collectstatic --noinput

# ۴) اجرای سرور WSGI
gunicorn config.wsgi:application -b 0.0.0.0:8000 --workers 3
```

- فایل‌های استاتیک توسط **WhiteNoise** بدون نیاز به وب‌سرور جداگانه سرو می‌شوند.
- با `DEBUG=False` تنظیمات امنیتی (XSS، nosniff، کوکی HTTPOnly، X-Frame) فعال می‌شوند.
- برای HTTPS، `CSRF_TRUSTED_ORIGINS` را در `.env` مقداردهی کنید.

## تم و ظاهر

رنگ‌بندی برند بر اساس لوگوی ویناک: ذغالی تیره + آبی فیروزه‌ای (`#0e9bd7`).
رابط فارسی، راست‌چین و Responsive با Bootstrap 5 و فونت **Vazirmatn**. کارت‌های
آماری با آیکون SVG، جدول‌ها و فرم‌های مدرن، ترنزیشن‌های نرم و احترام به

> فونت Vazirmatn از CDN بارگذاری می‌شود؛ در شبکهٔ کاملاً آفلاین به‌صورت خودکار به
> Tahoma بازمی‌گردد. برای آفلاین کامل می‌توان فایل فونت را در `static/fonts/` قرار
> داد.

## اتصال دستگاه تردد (فاز ۵)

مدل‌های `AttendanceDevice` و `AttendanceEvent` رویداد خام دستگاه را نگه می‌دارند
(`processing_status`: پردازش‌نشده/پردازش‌شده/خطا). پردازندهٔ `attendance/services.py`
رویدادهای «درخواست غذا» را با تطبیق `card_id` پرسنل به
`meals.services.issue_token` متصل می‌کند — قاعدهٔ «یک ژتون در روز» بدون تغییر اعمال
می‌شود.

**API داخلی دریافت رویداد** (محافظت‌شده با هدر `X-API-KEY` = مقدار `DEVICE_API_KEY`):

```bash
curl -X POST http://SERVER/attendance/api/events/ \
  -H "X-API-KEY: $DEVICE_API_KEY" -H "Content-Type: application/json" \
  -d '{"device_id":"R1","card_or_fingerprint":"CARD-1001","event_type":"meal_request"}'
```

پردازش دسته‌ای رویدادهای معوق (مثلاً به‌صورت کرون):

```bash
python manage.py process_attendance_events
```

> اگر `DEVICE_API_KEY` تنظیم نشده باشد، endpoint غیرفعال است (پاسخ ۵۰۳) تا
> به‌اشتباه باز نماند. اتصال واقعی سخت‌افزار در زمان نصب سازمانی انجام می‌شود.

## چاپ ژتون (فاز ۶)

صفحهٔ قابل‌چاپ هر ژتون در `‎/meals/token/<id>/print/` با QR Code تولیدشده در سمت
سرور (SVG درون‌خطی) در دسترس است؛ روی شبکهٔ داخلی بدون نیاز به اینترنت کلاینت کار
می‌کند.
